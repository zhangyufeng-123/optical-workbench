# 维护说明

## 常规维护

计划在每周一北京时间 09:00（Asia/Shanghai）检查 GitHub Issues、Pull Requests 和失败的 CI，优先处理能复现的启动、工程保存、连接、文字编辑及导出问题。定时执行由维护者在 Codex 中配置；本仓库本身不提供后台定时服务，具体任务状态以 Codex 定期任务为准。

修复在 `codex/` 前缀的分支进行。先确认问题和影响范围，再完成最小修改、相关回归验证及说明，通过 Pull Request 提交。保留已有用户工程格式；修改格式时提供兼容读取与必要的迁移说明。

依赖更新与功能修复分别处理。没有明确问题时不为凑更新而改动程序，也不因版本号较旧就跳过兼容性验证。

## 开发检查

在仓库根目录执行：

```powershell
npm ci
npm test
npm run build
npm run stage
```

GitHub Actions 执行同一套检查。逻辑测试包括连接与排版、文字状态保存、字体和导出结构等；DOM 替身测试不代表真实字体像素或鼠标操作已通过。

Windows 原生检查使用仓库中的 `qa/*.cjs` 和 `verify-portable.cjs`。涉及界面、字体或渲染的修改，应实际验证相应操作并查看截图。GPU 渲染检查依次运行，避免多个 Electron 检查争用显卡。

## 发布检查

1. 更新版本号、界面版本及发布说明，并保证源码与构建产物一致。
2. 完成相关逻辑测试和构建。对文字编辑、工程保存或渲染修改，验证预览、PNG、SVG 和完整包的一致性。
3. 生成 EXE 后核对包内程序与通过验证的构建一致，再实际启动 EXE、编辑、保存、关闭并重新打开，确认工程恢复。
4. 在 Releases 发布版本说明、Windows x64 EXE 和 SHA-256 校验文件。旧版本保持可追溯；发现问题时注明影响范围。

普通源码提交和 CI 不自动触发 Release；未通过验证的构建不能标成稳定版。

## 反馈处理

记录软件版本、Windows 版本、复现步骤、预期结果和实际结果。需要用户工程时，先尝试最小示例；只在确认范围后处理原始工程。

原生检查记录中的用户路径、缓存、浏览器配置、临时工程与密钥不进入版本库。对外提供测试结果时，说明验证范围，区分逻辑替身测试、真实桌面操作和真实 EXE 验证。

文献图例与外部模型的来源记录应随素材保留。新增第三方素材前核对实际来源与适用许可，不为来源不明的素材添加推测性授权。
